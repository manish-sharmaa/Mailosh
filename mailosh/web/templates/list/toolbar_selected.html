{# The toolbar with a selection (spec §6.1/§6.3). `list/toolbar.html` renders both bars and Alpine's `x-show` picks one: this file is the markup, not a second toolbar component, which is why it carries no surrounding element of its own beyond the bar. **Its controls act on the selection, and carry no ids of their own.** Every other `data-action` surface in this app (a row, the conversation view) sits on the thing it acts on and says which messages that is with `data-email-ids`. This one is deliberately the other shape: it lives outside every row, so actions.js's `targets()` falls through to `defaultTargets()` and reads the selection off the rows' own `aria-selected`. Copying ids into the toolbar would mean re-rendering it on every checkbox click, and the ids would be stale for exactly as long as it took to re-render. Every `title` names the key from static/js/keys.js's registry, spec §6.1's "Archive (e)". `tests/unit/test_mail_routes.py` checks the two against each other, so a rebound key cannot leave a stale hint here. Label as and Move to are live with 1D — `data-role` is the hook `static/js/labels.js` listens for, and the same two popovers `l` and `v` open, so the mouse and the keyboard cannot drift apart. More still belongs to the command palette and still says so rather than pretending: `aria-disabled`, no handler, no hook. `!== 0` rather than `> 0` — the exact complement of the other bar's `=== 0`, and no `>` inside an attribute value. Several tests scan these templates for element start-tags with a plain `<[a-z]+[^>]*>`, which is exact only for as long as that holds. The bare `x-data` is what makes Alpine look at this element at all; see `list/toolbar.html`'s header. Without it the `x-cloak` below is never removed and this bar can never appear. #}
